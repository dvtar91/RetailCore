**1. Функциональные требования (FR)**  

|  | Требование | Почему важно для трансформации |
|---|------------|--------------------------------|
| **FR‑01** | Оформление заказа — расчёт цены, применение скидок/акций, проверка наличия, выбор способа доставки и оплаты — должно работать в ≤ 2 сек при пиковых нагрузках (RPS ≈ 1500‑2000) | Это ядро бизнеса; любые задержки это падение конверсии и выручки |
| **FR‑02** | Универсальный “order‑core” — единый источник правды о состоянии заказа, доступный всем внутренним сервисам и клиентским UI (CRM, аналитика, партнёры) | Решает проблему разрозненных статусов и повышает прозрачность |
| **FR‑03** | Управление статусами заказа с расширяемой моделью и возможностью привязать к каждому статусу **причину** | Позволяет поддержке быстро отвечать клиенту и уменьшает ручные операции |
| **FR‑04** | Поддержка **мульти‑канального** входа (web, mobile, marketplace, API‑partner) без дублирования бизнес‑логики | Позволит запускать новые каналы без изменений в ядре |
| **FR‑05** | Гибкая система **платёжных и логистических интеграций** (plug‑in, event‑driven) с возможностью добавить/заменить провайдера без влияния на checkout | Снижает риск при добавлении новых партнёров |
| **FR‑06** | **История изменений** заказа (audit log) с возможностью фильтрации/поиска и экспорта для поддержки, аналитики и регуляторов | Требуется для SLA‑поддержки и расследования инцидентов |
| **FR‑07** | Возможность **частичного отмены/разделения** (split‑shipment) без потери согласованности данных и без ручных вмешательств | Уменьшает количество “ручных исключений” |
| **FR‑08** | API‑gateway с **универсальным контрактом** (OpenAPI/GraphQL) для всех внутренних и внешних сервисов, поддержкой версионирования | Обеспечит согласованность и упрощённую интеграцию новых сервисов |
| **FR‑09** | **Отчётность в реальном времени** о KPI‑order‑flow (конверсия, время до подтверждения, количество отклонений) с порогами Alarms | Даст бизнесу нужную прозрачность и предсказуемость |
| **FR‑10** | **Self‑service UI** для настройки новых промо‑правил, тарифов доставки и правил маршрутизации без разработки | Ускорит вывод коммерческих изменений |

**2. Нефункциональные требования (NFR)**  

|  | Требование | Примечания / критерии |
|---|------------|------------------------|
| **NFR‑01** | **Надёжность**: RTO ≤ 30 мин для критических подсистем (checkout, payment, status sync); RPO ≤ 5 мин для данных заказов | Ограничения из бизнес‑интервью (нельзя останавливать бизнес) |
| **NFR‑02** | **Доступность**: 99.9 % (p99) годовой uptime для order‑flow; p95‑p99 отклик ≤ 500 мс в часы пик |
| **NFR‑03** | **Производительность**: Система должна выдерживать 3× текущий пик‑нагрузки (≈ 6 000 TPS) без деградации основных метрик |
| **NFR‑04** | **Масштабируемость**: Горизонтальное масштабирование сервисов (stateless) и возможность добавления узлов без простоя |
| **NFR‑05** | **Согласованность**: **Strong consistency** внутри заказа (цена, статус) при взаимодействиях с внешними системами; **eventual consistency** допустима для аналитических реплик |
| **NFR‑06** | **Observability**: Полный набор метрик, трассировки (OpenTelemetry) и централизованный лог‑агрегатор; возможность быстрого построения “order‑timeline” |
| **NFR‑07** | **Безопасность**: GDPR‑совместимая обработка персональных данных, шифрование «in‑flight» и «at‑rest», RBAC на уровне сервисов и UI |
| **NFR‑08** | **Эволютивность**: Возможность внедрения новых сервисов/модулей без полной миграции (strangler‑fig pattern) |
| **NFR‑09** | **Ограничения инфраструктуры**: Сохраняем текущий on‑premise дата‑центр, но разрешаем **контейнеризацию (Docker/K8s)** и **VM‑уровневое** масштабирование; без полной облачной миграции |
| **NFR‑10** | **Снижение технического долга**: Максимум 30 % кода в новых сервисах покрыто unit‑/integration‑тестами, CI/CD‑pipeline с автоматическим rollback |

**3. Ограничения и допущения**  

|  | Ограничение / допущение | Требуется уточнение у |
|---|--------------------------|------------------------|
| **C‑01** | Нельзя просто «выключить» текущий checkout — бизнес‑операции должны работать 24 × 7 | Спонсор (Бизнес) |
| **C‑02** | База данных Oracle остаётся в эксплуатации минимум 12 мес; миграция в новую СУБД будет по‑этапно | Тех‑лид монолита |
| **C‑03** | Оборудование в дата‑центре ограничено в масштабировании — необходимо планировать вертикальное увеличение или добавление серверов с длительным закупочным циклом | Инфраструктурная команда |
| **C‑04** | Наличие «legacy» интеграций, реализованных через прямой SQL‑access (по‑мимо API) | Тех‑лид монолита |
| **C‑05** | Команды работают в разных технологических стеках (Java, Python, .NET) и не готовы сразу перейти к единой платформе | Тех‑лид монолита / Руководитель заказов |
| **C‑06** | Требования к SLA/SLO (время ответа, процент ошибок) не задокументированы полностью → **пробел**. Нужно уточнить у Спонсора и у команды эксплуатации |
| **C‑07** | Точные метрики p95/p99, RPS, максимальное время отклика в пиковые часы не известны → **пробел**. Требуется измерить (операционный мониторинг) |
| **C‑08** | Требования к консистентности (strong/evenual) для разных доменов (payment vs analytics) пока не сформулированы → **пробел**. Уточнить у Тех‑лидера и бизнес‑аналитиков |
| **C‑09** | Ожидаемый бюджет на трансформацию – не оговорён, только «последовательные инвестиции». → **пробел** (финансы) |
| **C‑10** | Требуется поддержка «многоязычности/локализации» (RU, EN) в UI и API‑responses – пока не упомянуто. Нужно уточнить у Спонсора |
