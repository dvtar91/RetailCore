> **Назначение** – показать последовательность шагов, которые позволяют перевести платформу RetailCore из текущего «монолитного» состояния в целевое промежуточное TO‑BE, не прерывая бизнес‑операции и контролируя риски.

## Этапы миграции (High‑level)

| Этап | Цель | Ключевые изменения | Промежуточное состояние (TO‑BE) | Планируемая длительность | Критерии завершения | Основные риски |
|---|---|---|---|---|---|---|
| **E1 – Подготовка инфраструктуры** | Подготовить стабильный брокер сообщений и CI/CD‑конвейер для микросервисов. | • Развёртывание Kafka‑like (1‑й кластер) <br>• Настройка docker‑runtime на существующих серверах <br>• Создание общей схемы `outbox` в Oracle. | Система готова к публикации/потреблению событий, но бизнес‑логика ещё в монолите. | 4 недели | • Брокер принимает/отдаёт сообщения без потерь <br>• CI/CD покрывает сборку и smoke‑тесты новых сервисов. | Плохая доступность брокера → задержка событий. |
| **E2 – Transactional Outbox + Event Bus** | Гарантировать атомарность записи заказа и публикации события. | • Добавлен `outbox`‑триггер в `OrderProcessingService` <br>• Запуск коннектора **Outbox‑to‑Kafka** (poll‑based). | Заказы записываются в Oracle, а событие `OrderCreated` появляется в топике. | 6 недели | • 99,5 % записей в `ORDERS` имеют соответствующее событие в топике <br>• Нет дублирования сообщений. | Ошибки репликации outbox → «потерянные» события. |
| **E3 – Выделение Order‑Core Service** | Перенести создание заказа из монолита в отдельный микросервис. | • Реализован `Order‑Core Service` (REST/GRPC) <br>• API‑gateway направляет **new‑order** запросы к новому сервису <br>• Оставлен синхронный вызов `paymentGateway` в монолите (fallback). | Первый канал (web) уже работает через Order‑Core, остальные каналы (mobile, marketplace) пока идут в монолит. | 8 недели | • Показатели p95‑latency checkout ≤ 500 ms <br>• Нет регрессий в оплате (тест‑платежи проходят). | Ошибки совместного доступа к `ORDERS` (конфликты записей). |
| **E4 – Вынос PromoEngine** | Снять расчёт скидок из монолита в отдельный сервис. | • Создан `PromoEngine Service` (REST) <br>• `Order‑Core` вызывает его через HTTP, fallback к PL/SQL при недоступности. | Все новые промо‑правила внедряются в PromoEngine, legacy‑правила остаются в PL/SQL. | 6 недели | • % fallback‑вызовов < 5 % в продакшн <br>• Тесты на совпадение результатов с legacy‑расчётом. | Несогласованность discount‑values → клиент видит неправильную цену. |
| **E5 – Integration Facade (логистика)** | Убрать staging‑таблицы, унифицировать обмен с доставкой и маркетплейсами. | • Создан `Integration Facade` (REST + очередь) <br>• Перенаправление всех `reserveSlot`‑вызовов через фасад <br>• Старая .NET‑служба оставлена в режиме read‑only. | Новые заказы получают статус `RESERVATION_PENDING` из фасада, а старые остаются в legacy‑пути. | 8 недели | • Доля заказов, проходящих через фасад ≥ 80 % <br>• Ошибки дублирования доставок < 0,5 %. | Партнёры не поддерживают новый API → возврат к старой схеме. |
| **E6 – Status Service (state‑machine)** | Централизовать модель статусов, избавиться от ручных правок. | • `Status Service` потребляет `OrderCreated`, `PromoApplied`, `DeliveryConfirmed` <br>• Публикует `OrderStatusChanged` <br>• UI‑поддержки переключено на чтение из сервиса. | Полный цикл статусов управляется сервисом; монолит использует только событие `OrderCreated` и больше не меняет статус. | 6 недели | • Ручные вмешательства ≤ 425 / мес <br>• Статусы в UI совпадают с тем, что публикует сервис (> 99 %). | Ошибки в state‑machine → застревание статусов. |
| **E7 – Read‑Model & Analytics** | Перейти аналитику с прямого чтения Oracle на Event‑driven модель. | • Консьюмер `Analytics Service` строит денормализованные витрины в PostgreSQL/ClickHouse <br>• Отключение nightly‑SQL‑экспортов. | Аналитика полностью оторвана от оперативной БД, нагрузка на Oracle снижается > 40 %. | 8 недели | • Объём запросов к Oracle уменьшен на ≥ 40 % <br>• Данные в витрине соответствуют событиям (30‑минутный SLA). | Отставание событий → неполные отчёты. |
| **E8 – Финальная стабилизация** | Вывести из эксплуатации оставшиеся PL/SQL‑функции, удалить .NET‑интегратор. | • Перенос последних бизнес‑правил в микросервисы <br>• Отключение `LegacySqlExecutor` в Order‑Core <br>• Декомиссия .NET‑службы. | Монолит остаётся только как thin‑wrapper для payment‑orchestration (может быть полностью выключен позже). | 4 недели | • Все бизнес‑правила покрыты тестами <br>• Нет вызовов к `legacy_promo_pkg` и к staging‑таблицам. | Потеря функциональности, если миграция неполная. |

## Управление рисками

| Риск | Приоритет | План снижения | План реагирования |
|---|---|---|---|
| **Outbox‑lag > 30 сек** | Высокий | Мониторинг `outbox`‑offset, алерт, авто‑перезапуск коннектора. | Переключить обратно на прямой DB‑чтение (feature‑flag) до исправления. |
| **Fallback‑promo > 5 %** | Средний | Тестовый покрытие > 95 % бизнес‑правил, canary‑деплой PromoEngine. | Временно отключить новый PromoEngine, вернуть PL/SQL. |
| **Неподдерживаемый API партнёра** | Средний | Договориться о версии API до начала миграции, подготовить shim‑слой. | Откат к старой схеме через staging‑таблицы, фикс‑плейсхолдер. |
| **Потеря согласованности статусов** | Высокий | Idempotent‑обработчики, двойная запись в `OrderStatusLog`. | Перезапуск `Status Service` с восстановлением из `ORDERS` + `outbox`. |
| **Перегрузка брокера** | Низкий | Прокачка партиций, резервный брокер‑кластер. | Переключить продюсеров на резервный кластер, включить back‑pressure. |
| **Отказ инфраструктуры (CPU/Memory)** | Средний | План capacity‑planning, распределение контейнеров по серверам. | При росте нагрузки – добавить новые узлы, переместить тяжелые сервисы. |

## Критерии завершения программы

| Критерий | Порог |
|---|---|
| **Latency checkout (p95)** | ≤ 500 ms (измеряется в продакшн после E3). |
| **Ручные вмешательства** | ≤ 425 / мес (после E6). |
| **Нагрузка на Oracle** | Снижение TPS запросов минимум 40 % (после E7). |
| **Availability Event Bus** | 99,9 % (в течение 30 дней после E2). |
| **Отказоустойчивость** | Возможность отката любого микросервиса в ≤ 5 мин без потери данных (тестировано в стейдж‑окружении). |

## Управление изменениями

* **Change‑Control Board (CCB)** – еженедельные встречи с представителями всех команд.  
* **Feature‑flags** – каждый новый сервис включается в продакшн лишь для части трафика (canary).  
* **Rollback‑policy** – каждый релиз сопровождается скриптом отката и проверкой состояния данных (см. Cutover‑Plan).
